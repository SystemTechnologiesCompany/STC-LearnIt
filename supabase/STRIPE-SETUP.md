# Deploy STC Learnit card subscriptions

These files implement Stripe-hosted monthly Checkout and Customer Portal, signed payment webhooks and separate subscription entitlements. They have not been deployed or tested against your Stripe/Supabase accounts. No API key is included in these files.

## 1. Database

In Supabase SQL Editor, run `stripe-billing.sql` after the existing `premium-codes.sql` setup. It preserves activation-code purchases. It upgrades the deployed energy function to read the combined membership view. If you rerun an older learning-energy/pro-energy-regeneration script later, rerun stripe-billing.sql afterward too.

Sandbox payments are recorded but intentionally do not grant premium benefits on the production website. Inspect `stripe_subscriptions.paid_until`, tier and mode to validate sandbox fulfillment. To exercise premium UI/energy with sandbox entitlements, use a separate staging Supabase project and change the staging view to include sandbox rows there only.

## 2. Supabase secrets

Keep your restricted sandbox key in `STRIPE_SECRET_KEY`. The function uses the Supabase-provided `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` on the server. Add:

| Name | Value |
| --- | --- |
| STRIPE_MODE | test |
| STRIPE_PRICE_PRO | price_1UZ7jk4Mzb2FMoC9REskIl6F |
| STRIPE_PRICE_STC | price_1UZ7k54Mzb2FMoC9htZNQwMR |
| STRIPE_WEBHOOK_SECRET | Copy privately from the Stripe event destination created below |

Both Prices must belong to the same sandbox as the API key, be active, recurring monthly, and have amounts 250 DZD and 700 DZD respectively. DZD amounts in the API are 25000 and 70000 minor units. A key/environment/currency/amount mismatch fails closed. Never put keys in website files or chat.

Restricted key permissions required by this implementation: Customers write; Checkout Sessions write; Prices read; Subscriptions read; Invoices read (including line items and invoice payments); Charges read; Customer Portal Sessions write. All other permissions can remain disabled. Permission names/grouping may differ in Stripe Dashboard. Configure the Customer Portal separately through the Dashboard.

## 3. Deploy Edge Functions

Deploy both folders and their shared module together using Supabase CLI from this checkout:

```sh
supabase functions deploy stripe-billing --project-ref mftftfqvfqlfzqprtpih --no-verify-jwt
supabase functions deploy stripe-webhook --project-ref mftftfqvfqlfzqprtpih --no-verify-jwt
```

`stripe-billing` checks the actual Supabase user token itself with Auth. The webhook must accept requests without Supabase JWTs; it validates Stripe signatures instead. For Dashboard deployment, paste the corresponding self-contained file from `supabase/dashboard/` into the editor. Those generated bundles include the shared code; the original index.ts files alone require the shared module to be included separately. Disable the platform's JWT verification for both functions; their code performs the appropriate authentication/signature validation.

## 4. Stripe event destination

In the same Stripe sandbox, create an event destination/webhook for this account:

`https://mftftfqvfqlfzqprtpih.supabase.co/functions/v1/stripe-webhook`

Select API version `2026-10-28.endive` to match the server integration. Subscribe only to:

- checkout.session.completed
- checkout.session.async_payment_succeeded
- checkout.session.async_payment_failed
- customer.subscription.created
- customer.subscription.updated
- customer.subscription.deleted
- invoice.paid
- invoice.payment_failed
- charge.refunded
- charge.dispute.created
- radar.early_fraud_warning.created

Copy its signing secret into `STRIPE_WEBHOOK_SECRET` privately. Do not use an API key as a webhook secret. Failed reconciliations return HTTP 500 for Stripe retry; invalid signatures return 400. Customer mappings missing at event delivery are retried. Event IDs are stored transactionally with subscription updates. Older snapshots cannot overwrite newer observed state.

## 5. Customer Portal and invoicing

Enable invoice history/downloads, payment-method updates and cancellation at the end of the paid period. Disable trials, promotions, quantity edits and subscription plan switches for this first release. Upgrades/downgrades require a deliberate proration/access policy before enabling them. Subscription invoices are generated by Billing; there is no separate manual invoice-sending action in this release.

Access lasts through the last confirmed paid invoice period, including after end-of-period cancellation or a failed renewal until previously paid time expires. No extra unpaid grace period is granted. Full refunds and disputes block that Stripe entitlement pending manual review; partial refunds leave access intact. Early fraud warnings are logged for Dashboard review without an automatic ban. To clear a resolved risk block, an administrator must reconcile the Stripe state and update `risk_blocked` in Supabase. Code-based access is unaffected by Stripe risk events or cancellation.

Tax: review applicable registrations before launch. Automatic tax is not enabled by this code. Configure Stripe Tax only after the required registrations are active, and review how inclusive/exclusive tax affects the advertised prices.

## 6. Website and sandbox validation

Publish `plans.js` and `premium-theme.js` through the existing GitHub/Netlify workflow after deploying the database and functions. The Visa option calls `stripe-billing`; it never receives an API key. The return page displays a pending-confirmation notice and does not itself activate a membership. The membership modal also links to the authenticated Customer Portal.

Also publish `supabase-config.js`. It keeps `stripeMode: 'test'` during sandbox testing: normal visitors see the coming-soon message, and explicitly visiting `https://stclearnit.netlify.app/profile.html?billing_test=1` enables clearly labelled sandbox checkout. This query is a test-mode convenience, not an authorization control; sandbox payments still grant no production entitlement. Set stripeMode to live only at the verified live release.

Validate signed-in Pro/STC checkout, correct amounts/currency, payment decline, abandonment, signature rejection, duplicate/reordered deliveries, paid renewals, failed renewal, cancellation, refund/dispute review, and independent code purchases. Check the Stripe event delivery response and Supabase function logs. Validate Customer Portal access with two distinct user accounts. Never use real cards in the sandbox.

## 7. Live release

Before accepting money, confirm Stripe charges and payouts are enabled for the verified merchant account. Rotate the live key previously shared in chat. Create live Products/Prices, replace both Price secrets, use a new restricted live key, set STRIPE_MODE=live, create a separate live event destination/signing secret, and repeat launch checks. Sandbox Price IDs and secrets cannot be used for live checkout. Do not enable live mode merely to bypass a mode mismatch.

## Limits

Local syntax/type validation is not a payment test. Database migration and real webhook delivery still need validation against the sandbox. The production website currently permits CORS requests only from `https://stclearnit.netlify.app`; add an explicitly allowed staging origin to the server code for a separate staging deployment. If a plan is archived, preserve its configured Price ID for subscription reconciliation and consider making a new checkout price configuration before changing the public catalog.
